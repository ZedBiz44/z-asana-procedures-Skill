# Zed Asana Procedures

Build work a person can understand and complete. Prepare it unassigned, read the actual result back, then assign it. These are agent instructions, not an automated Asana validator.

## Route and read what applies

- Read the complete request and its actual source files. Identify the outcome, scope, deliverables, people, destination, timing, review, and approval limits.
- For project setup or structural repair, use `z-advanced-asana-control` for authority and connection checks; this skill owns how to build. For executing assigned work or a small follow-up within it, use `z-asana-agent-control`. Do not load both execution workflows just to select an identity.
- Use `z-agent-communication` for descriptions and messages. Write for the worker, using everyday English at about Grade 8 and no higher than Grade 9–10.
- Search for existing work before creating it. Preserve useful IDs, comments, proof, and approvals during repair. Never guess people, dates, links, or permissions.
- Diagnose mode permits inspection and proposals. Get-er-Done mode permits the authorized work. Existing authorization counts; broader or destructive changes follow advanced control.

## Plan the smallest usable structure

- Use a project for several independently managed results, a main task for one result, and a subtask for one independently finishable result or meaningful work step with an observable done condition.
- Split outputs when different inputs, owners, timing, reviews, or proof need separate tracking. Keep tiny same-owner checks together. Do not impose a fixed task count or turn every click into a subtask.
- Start each actionable task and subtask title with a verb. Do not add number prefixes. Present draft task lists as bullets, not numbered lists, so numbering is not copied into Asana. Native section headings are exempt from the verb rule.
- Include production, review, corrections, delivery, and proof where needed. Normally use main tasks plus one level of actionable subtasks.
- Plan intended owners without assigning them yet. A VA section is organization, not an assignee. Children do not inherit their main task's assignee.
- Establish working order, including real prerequisites. Dates and dependencies do not establish visible list order.
- Confirm the approved tools can create any required native subtask dividers and set ordering before repeating a structure. Never use ordinary tasks or extra nesting as fake headings. Report a missing capability and hold the affected setup.

## Build one complete example, then repeat

When several VAs or tasks share a pattern, build one complete representative path through preparation, production, review, and delivery. Leave it unassigned. Read its descriptions, links, dividers, relationships, and visible order back before copying the pattern. Correct defects first. A single task does not need a separate pilot project.

- Start each main-task description with **Deliverables**: name each required output and provide its working-link, final-link, and proof slots. Mark only not-yet-produced results pending.
- Give every actionable item enough context to work from My Tasks: purpose, exact source, action, output, save location, completion check, and any wait or review condition. Link reusable SOPs instead of copying whole manuals.
- Set relevant dates and genuine dependencies. Physically position sections, tasks, and subtasks in working order using supported placement controls; confirm the returned order.
- For a project or queue, fill the continuation instructions in the project brief and affected tasks. Use the linked continuation reference rather than inventing a new logging or monitoring system.
- Prevent template defaults, imports, forms, recurrence, and rules from assigning incomplete work. A Setup section, future date, or label does not suppress notifications. Use a safe unassigned route or stop that operation.
- For already assigned work, do not automatically unassign it. Prepare the complete correction, assess whether workers need a pause, and preserve accepted work. Unassigning does not recall earlier notifications.
- If assigned too early, promptly explain what must wait through an authorized worker communication route; if none is authorized, flag the required pause to the requester. Finish and recheck before release.
- If inputs are missing, prepare independent work and ask the responsible person for the exact missing information.

## Check the release batch, then assign

Read actual Asana objects back. A successful write, task count, or agent's assurance is not proof. Check the entire assignment or self-contained release batch before its first assignment notification.

| Check | Required result |
| --- | --- |
| Structure and order | Correct project/team, sections, relationships, native dividers, and actual section/task/subtask display order; subtasks sit under the intended divider. |
| Titles and descriptions | Unnumbered action titles; Deliverables first on main tasks; each actionable item's instructions make sense alone. |
| Inputs and access | Required sources and destinations are exact and usable by intended workers. Creator access alone proves nothing about worker access. Resolve required access and missing inputs before release. |
| Work and people | Complete breakdown, intended owner for each actionable item, relevant dates, genuine dependencies, clear reviewer and wait conditions. No auto-assignment path remains. |
| Continuation | For projects/queues, the owner, next-item rule, local/global stops, reporting fallback, checkpoint, and real review/resume arrangements pass the continuation reference. An untested monitoring promise is insufficient. |

After all required checks pass, set each intended main-task and subtask assignee. Read every assignment back. A complete future step may be assigned with a clear wait condition. Assignment does not prove receipt or that work started.

If a required check fails, correct it or report **Prepared but not released** with the exact gap. Never say ready or verified while required structure, content, access, or assignment remains missing. Record the result on the existing task/project or authorized work record; do not invent another checklist destination.

## Work, review, and finish

Follow the delivery reference. Keep the current brief in the description and decisions in comments. Keep the main task with its delivery owner during review. Use a draft/handoff subtask as the review prerequisite; do not make review depend on completion of the main task that itself needs approval.

Continue the next independent authorized item while another awaits review. Hold only the affected work when a local problem or reporting failure occurs, as the continuation reference directs. Finishing one item does not complete a queue.

A test assignment may finish with documented failures and owned corrections if that is its promised result. An assignment promising a working result needs passing acceptance or an explicitly approved exception.

## Handle failures and report honestly

- After an ambiguous write, inspect current state before retrying. Do not duplicate work or assignments.
- Stop the affected operation after three failed attempts, or immediately for identity, permission, authorization, or materially expanded scope. Continue only known safe, independent, authorized work; explain any project-wide stop.
- Preserve the last usable state. Do not delete partial setup or redo completed business work to repair logging.
- Return exact links, changes, checks, assignment status, remaining gaps, and next action. Distinguish **Ready and assigned**, **Prepared but not released**, and **Business work complete**.
- Keep task decisions and proof in Asana. Follow applicable agent-control activity-memory rules when a separate record is required; record technical changes in GitHub and significant operational work in the Technical Journal. Use Mountain Time for timed commitments.
