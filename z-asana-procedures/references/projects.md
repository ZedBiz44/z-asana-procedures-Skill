# Projects

## Choose the project

Search the intended team and existing work first. Keep a small repair in its existing support project. Create a new project when several deliverables, stakeholders, or schedules need their own coordination, or when an ongoing queue needs a shared home. Confirm the team, project owner, purpose, scope, privacy, contributors, and acceptance authority.

The coordinator builds structure and keeps the queue moving; the project owner owns the whole outcome. Do not make the coordinator the default owner of every task. A project is not ready merely because its tasks exist: complete and verify the continuation block in the brief assets, including the next-item rule, local/global stop conditions, reporting fallback, review delivery, and interrupted-run responsibility.

Use an approved template when suitable. Inspect its saved assignees and automation before making a copy. A reusable master is not an active delivery project. Preserve live work when repairing; do not move or delete unrelated records without authority.

## Write the project brief

Use the project format in the brief assets. Name the business result, measurable success, scope, deliverables, roles, authority, timing, resource links, update rhythm, and final acceptance. Name the client or venture and outcome in the title. Avoid generic names such as “New project.” Keep the brief current after approved changes.

## Create project sections and place tasks

Choose one understandable section pattern:

- Stage sections for a simple queue: Intake, Ready, In progress, Review, Waiting.
- Workstream sections for parallel delivery: Content, Website, Automation, Launch.
- Phase sections for a staged build: Planning, Production, Testing, Delivery.
- The existing approved cycle for ongoing content work.

Do not mix people, phases, and channels in one section list. Choose one authoritative source of task stage. If sections represent workstreams, use an existing approved stage field only when needed.

In the project List view, use Add section, name the section, and arrange sections in working order. Add tasks beneath the intended section or move existing tasks into it. Through agent tools, resolve the actual section ID and use supported placement/reorder operations. Read back the actual membership and order.

Sections group project tasks; subtask sections divide a task's child list. A Board column grouped by a field is not necessarily a native section. Check grouping before changing placement or rules. Section deletion follows the authority rules and requires inspection of what happens to contained tasks.

## Views and project workflow

- List shows assignments, owners, dates, and supporting work.
- Board shows stage or chosen grouping.
- Calendar shows dated work; inspect filters and project association if a task is missing.
- Timeline/Gantt, when available, supports schedule and dependency review.
- Dashboards summarize maintained data, not proof of business results.

Fields store structured information. Rules react to events. Set up the manual workflow first and inspect both before release. Do not create competing status fields or automatic assignment during setup.

## Status and closeout

At the agreed cadence, inspect overdue work, next milestones, missing owners, blockers, review queues, dates, and capacity. Post health and its reason, delivered results, upcoming commitments, risks, required decisions, and approved scope changes. Project health is different from individual task stage.

Before closeout, verify final acceptance, output links, ongoing ownership, unresolved exceptions, and deliberate placement of follow-up work. Archive only with the required authority; preserve useful history. A completed-task percentage does not prove leads, sales, or client results.
