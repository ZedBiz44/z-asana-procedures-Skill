# Tasks and subtasks

## Create a clear task

Use one accountable owner per released task. Create an action title that makes sense in My Tasks, such as “Test the booking form and record the result.” Put the task in the correct project and section. Keep it unassigned during preparation.

Write the expected result, purpose, exact work, source links, limits, output destination, relevant timing, completion checks, and reviewer/approval requirements. Put working and final deliverable links near the top. Link reusable SOPs rather than pasting long general instructions, but include enough context to start without reconstructing chat history.

For a small job, a short Action / Reference / Done when / Save here format is enough. Remove missing-input placeholders before release; leave not-yet-produced output links clearly marked pending.

## Choose useful subtasks

Start with the main task's outcome. Include each required action once. Use a subtask when ownership, timing, discussion, proof, or review needs separate tracking. Tiny checks with the same owner and timing can remain checklist items.

Open the main task, add a subtask with a result-led title, leave it unassigned, and fill its inputs, action, destination, completion check, and wait conditions. Make it understandable when opened directly from My Tasks. Add relevant dates and real dependencies. Verify its parent and display position.

Keep nesting shallow. If work becomes independently managed, consider a separate main task or project while preserving links and history. Counts alone do not decide the structure.

## Create real subtask sections

For multi-stage lists, use native subtask section dividers such as Prepare, Produce, Review and correct, Deliver. Match these names and their order to the main description.

In Asana's web interface, focus inside the subtask list and use Tab + N. Verify the divider appears inside that main task, and the action subtasks sit beneath the intended divider. Through tools, use a verified supported native-section operation; a tool called “create section” may support only project sections, so inspect its schema and read the result back.

Never fake a section with an ordinary task titled “SECTION — Research,” an unassigned heading task, or an extra nesting level. If native subtask sections are required and unsupported, stop that setup step and report the missing capability. Keep actual subtasks correctly attached.

## Ownership, visibility, and shared tasks

Subtasks have their own assignees; setting the main-task assignee does not assign its children. Check relevant field availability separately from project membership. Official help has contained conflicting first-level custom-field inheritance wording, so inspect the actual child and intended report rather than guessing.

If a subtask must appear on the project calendar, check its due date, project association, and view filters. Do not create a duplicate merely to make it visible.

Multi-homing means adding the same task to another project. Confirm authorization and destination audience before adding it. The task's shared access can change; a restrictive project does not erase access from other projects. Read back membership and intended visibility.

## Repair existing work

Read all relevant descriptions, comments, subtasks, dependencies, dates, and accepted work first. Preserve IDs and usable history. Identify requested changes and prepare a complete replacement brief before editing active assignments. Explain any required pause. Do not assume changing or removing an assignee is silent.
