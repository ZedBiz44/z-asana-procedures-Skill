# Fields, rules, dates, and reuse

## Native and custom fields

Use native assignee, due date, and completion controls. Use existing approved priority/stage fields when applicable. A field should support a real filter, decision, report, or rule; prose instructions belong in the description.

Inspect the existing library and actual field/option IDs before adding anything. Same field names do not prove shared identity. Before an authorized new field, define purpose, object level, type, options, units, owner, required use, and affected rules/reports/templates. Shared changes follow the advanced authority procedure.

In the project Customize menu, use Fields to add an approved existing field. Set values on relevant tasks and inspect intended views and reports. Do not invent a universal field set or new Priority values from the draft guide. Check subtask field availability independently.

## Dates, dependencies, and milestones

A due date is the required verified finish. Allow time for production, review, correction, and delivery. Separate effort from elapsed time. Use Mountain Time for timed commitments and state it explicitly.

Add native dependencies only for real prerequisites. Resolve the predecessor and successor IDs and verify the relationship. Preferred reading order is not a dependency. A date change requires checking downstream work and actual date-shift settings; never assume all dates moved correctly.

Use milestones for meaningful acceptance gates. Keep uncommitted ideas in a reviewed backlog. If delivery cannot be dated yet, give the necessary clarification/planning work a date instead of inventing a promise. Check capacity before releasing a batch and avoid counting the same effort on both main tasks and subtasks.

## Templates and recurrence

Choose task templates for one repeatable assignment and project templates for coordinated deliverables. Inspect the approved template and resulting instance, not just its name. Replace client details, working links, final destinations, dates, access, and input placeholders. Keep intended roles without live assignees during setup. Check copied dependencies and hard-coded links: duplication may preserve references to the master.

Use known suitable Asana templates as they become available. The bundled brief formats are writing aids, not installed Asana templates. Do not create a template library unless requested.

Recurring tasks can copy fields and subtasks when the next occurrence is generated. Do not make both the main task and its children recur. Use separate dated tasks if all future occurrences must be visible now. If each occurrence needs new inputs, do not auto-release an unfinished instance; prepare unassigned work and apply the core release gate.

## Project rules

Rules use triggers, optional conditions, and actions. In the project Customize menu, open Rules and choose an available rule or supported custom rule. Record its purpose, trigger, conditions, actions, affected work, owner, and disable/recovery method.

Before activation, inspect permissions and available plan features. Test a matching case, non-matching case, reopened item, and relevant subtasks in an authorized controlled workflow. Check for loops, duplicate creation, premature assignment, and false completion. Verify rule scope rather than assuming rules cover every subtask.

Automatic assignment must not occur during setup. A Setup section alone is not a protection. An explicit readiness condition is useful only when the whole assignment is actually checked before that condition is set. No rule may mark promised work complete without its required checks.

## Forms

Use project Customize → Add → Forms when supported. Collect requester, requested result, inputs, constraints, timing, and destination. Map answers to existing fields where helpful; inspect title, destination section, and assignee defaults. Publish only within authorization and test the resulting task and rule effects.

Submission means intake, not automatic delivery readiness. An assigned triage task must itself have a complete instruction and clear result. If templates, forms, or rules can assign prematurely, stop that creation path until a safe unassigned route is available.
